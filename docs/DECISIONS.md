# Decision log (ADR-lite)

One entry per design choice: context, decision, alternatives considered, consequence. This is the crib sheet for defending the design in review — kept up to date as the build progresses, not written after the fact.

Standards followed: see `artifacts/adopted_standards.md` for the general Python/testing/security/git conventions this project holds itself to.

---

## D0 — Grounding: pure computer-use toolset, not a DOM-ref custom tool
**Context:** the brief asks for an approach that still works with no clean DOM (legacy web, desktop).
**Decision:** discovery perceives via screenshots + coordinates (`computer_toolset_20260801` on `claude-opus-5-5`), with a compact on-screen element list sent alongside each screenshot as a grounding aid only — the model still acts by coordinate, never by element reference.
**Alternatives:** a custom `act_on(element_ref, action)` tool keyed to DOM/AX nodes — rejected as the primary channel because it silently assumes a clean, queryable tree, which legacy apps and canvases don't have.
**Consequence:** every click must be resolved to a real element *after* the model acts, via hit-testing (see D1) — coordinates never make it into the artifact.
**Reversal cost:** ~4h if the G0 spike shows this doesn't work; the pre-decided fallback is the DOM-ref tool, with the recorder and compiler unchanged downstream of the resolver.

## D1 — Record-time targeting: multi-strategy, validated before it's kept
**Context:** replay must survive label/wording drift, nested tables, framesets.
**Decision:** on every acted coordinate, hit-test through frames (`elementFromPoint` + frame offsets) → snap to the nearest interactive ancestor → generate ranked candidate strategies (form `name=`/`value=` attr, role+name, label-anchor+relation, table row×column, exact text, structural path relative to an anchor, visual fallback) → keep only strategies that resolve uniquely back to the same element.
**Alternatives:** record the raw CSS/XPath selector Playwright would generate — rejected, these break on any markup reshuffle, which is explicitly called out as a risk in the brief.
**Consequence:** the recorder must run the *replay-time* resolver during discovery, not just during replay — this is the equivalence guarantee (S8's acceptance criterion).

## D2 — Discovery acts through the resolved element, never the raw coordinate
**Context:** if the model's coordinate and the recorded target can silently diverge, discovery "succeeding" doesn't guarantee replay will do the same thing.
**Decision:** the action dispatcher always re-resolves and acts on the handle the resolver found, not the literal (x, y) — so what was recorded is provably what happened.
**Reversal cost:** none to keep this; reversing it voids the equivalence guarantee entirely.

## D3 — Login is scripted, outside the LLM loop
**Context:** the model must never see credentials (safety requirement, §3.4 of the brief).
**Decision:** login runs as a fixed script before discovery starts; the same script is the replay/retry re-login handler on session expiry. In-flow secrets (if any) are filled via a `type_secret(target, ref)` tool scoped to an allowlisted field — the model only ever sees a reference, never a value.

## D4 — Result contract: a discriminated union, not a single success/failure
**Context:** §3.3 of the brief explicitly requires separating "no such member" (a legitimate answer) from a crash.
**Decision:** `succeeded | business_outcome | failed | escalated | blocked_pending_approval`, each its own Pydantic model. `failed` carries a closed set of error codes plus step/expected/observed/evidence.
**Consequence:** a calling agent's dispatch logic is a `match` on `status`, never string-sniffing an error message.

## D5 — Business-outcome detectors come from a second live probe run, not a separate classifier call
**Context:** discovery only sees the happy path on the first run; detectors for "member not found" etc. must come from somewhere, and literal LLM output must never leak into the artifact (compile-time literal deny-by-default, D6).
**Decision:** after the happy-path artifact compiles, replay it against a probe input known to diverge (e.g. a nonexistent member ID) using the *compiled* artifact — if it fails with no matching detector, snapshot the divergent state and propose a `TextPresent` condition from it, checked against both the divergent state and every happy-path state (so it can't match the success page too).
**Alternatives:** a bounded one-off LLM call that looks at the divergent screenshot and classifies it — simpler, but adds a model call with no replay-determinism guarantee behind the proposed condition; rejected per the buildout plan's gate-sharpening pass.
**Reversal cost:** ~1h to fall back to a human-authored detector if probe-based discovery proves unreliable.

## D6 — Literals are deny-by-default at compile time
**Context:** the brief requires never persisting secrets or raw PII into artifacts.
**Decision:** the compiler only accepts a literal value if it equals a declared input parameter (→ parameterized) or is in a reviewer-approved `allowed_literals` list; anything else fails the compile outright, loudly, rather than being silently redacted.
**Consequence:** a captured member name or account number can never accidentally end up baked into a selector or checkpoint string.

## D7 — Safety: a single `act()` choke point + route-scoped commit deny list
**Context:** prompt injection via on-screen text (e.g. a note field saying "ignore instructions, transfer funds") must not be able to widen what the agent is allowed to do.
**Decision:** every action — from the LLM loop, from replay, from an approved human step — passes through one `act()` function: lease check → resolve the *live* element and classify what's actually there → policy check (origin/route/action-type allowlist + risk class) → act under lock → post-action URL/popup check. A network-level guard in `context.route` blocks state-changing requests to routes on a deny list, rather than a blanket time-windowed "commit grant" — because legacy apps often POST even for reads (e.g. member search), so blocking all non-GET traffic would break the happy path.
**Alternatives considered (buildout-plan simplification):** an HMAC-signed, single-use approval token bound to (capability, version, params, nonce, exp) for risky actions — simplified to a plain single-use approval record (still non-reusable, still tied to the artifact's content hash) since a cryptographic signature adds no real protection in a single-process, single-operator take-home context.
**Reversal cost:** ~1h to add HMAC signing back if a reviewer wants it; ~2h to revert the deny-list to a time-windowed guard if route coverage proves incomplete.

## D8 — Human handoff: the terminal is the authoritative control channel
**Context:** the brief requires a real control-transfer model, not just a TODO. Anything running inside the browser page (an in-page "hand back" button, a recorder binding) can in principle be called by page JavaScript itself — including injected content.
**Decision:** a control lease with a fencing epoch (bumped on every holder change) gates the single `act()` function; the *terminal*, outside the browser process, is the only channel that can claim control, approve a risky action once, deny, or hand back. An in-page banner shows who's in control as a convenience; an in-page button (if built) only requests a handback, it doesn't grant one.
**Consequence:** a stale LLM decision in flight when a human takes over carries an old epoch and is rejected (`ControlLost`) rather than silently racing the human's actions.

## D9 — Evidence: discovery capture happens once, replay evidence regenerates
**Context:** the live discovery run costs real tokens and real time (and real LLM non-determinism); replay is supposed to be free of both.
**Decision:** the committed discovery evidence (raw model responses, screenshots, the compiled artifact) is captured once and checked into `/evidence/`, not regenerated on every `make evidence` run. Replay evidence (business outcome, recovered fault, hard failure, handoff) regenerates every time, since it's deterministic and costs nothing.

## D10 — What we are not building
Per the brief's explicit penalty on scaling infrastructure: no tenant-overlay engine, no operator web console, no desktop surface implementation, no queues/services/Docker/CI. These get a design section in REPORT.md (§4 Heterogeneity & multi-tenant, §5 Escalation & handoff) instead of code. See `artifacts/buildout_interface-ai-cua_take-home.md` §"What NOT to build" for the full list and reasoning.

## D11 — Schema trimmed to the buildout plan's keep-set
**Context:** the first schema draft (from the architecture-review pass) was workable but ~30% wider than a 36h build justifies — every field has to be defensible in REPORT §2 and in follow-up questions.
**Decision:** dropped `quorum` and `min_confidence` per step, per-step `page_signature` in provenance (kept one, single value, on `Checkpoint` instead), the `FieldValueEquals` condition (covered by `TextPresent` + scoped `ElementResolvable`), and the separate tenant-overlay/drift-engine code (now design-only, see D10). Kept everything in the "Keep in v0" column of `artifacts/buildout_interface-ai-cua_take-home.md` §2.
**Consequence:** a `Step`'s only proof that an action "worked" is its `post` condition — there is no per-field value-equality check. Acceptable because the compiler (S9) will separately verify extracted output values against what discovery claimed (see buildout plan item 12), which is the check that actually matters.

## D12 — `extra="forbid"` on every artifact model, as the anti-coordinate guard
**Context:** D0/D1 require that raw coordinates never reach the artifact — this needs to be enforced, not just intended.
**Decision:** every Pydantic model in `artifact/targets.py`, `artifact/conditions.py`, and `artifact/schema.py` sets `model_config = ConfigDict(extra="forbid")`. A stray `coordinate` field on a `Strategy` or `TargetDescriptor` — e.g. from a future compiler bug that serializes a raw click point — fails validation immediately instead of silently round-tripping.
**Consequence:** this is a structural guarantee, not just a lint rule or code-review habit; tested directly in `test_artifact_schema.py`.

## D13 — Resolver: ambiguity never falls back to first-match; strategies fail through to the next
**Context:** S5's acceptance criterion is explicit — "ambiguity returns target_unresolved, never first-match." A resolver that silently picks `.first` on an ambiguous locator is exactly the failure mode that makes replay unreliable on legacy markup (duplicate submit buttons, repeated labels).
**Decision:** `resolve()` tries each strategy in rank order; a strategy whose candidate set has 0 or >1 valid matches (after the `expect` filters) is recorded as a failed attempt and the next strategy is tried. Only a strategy that resolves to *exactly one* valid element is chosen. If no strategy uniquely resolves, the result is `handle=None` with the full attempt history — never a guess.
**Found by this discipline:** the `table_cell` strategy's JS initially matched the *header row* instead of the data row, because our app's table header literally repeats the row-anchor text (`<th>Regular Savings</th>` above `<td>Regular Savings</td>`) — a real instance of the "label text isn't unique on the page" problem this whole design exists to handle. Caught immediately by a table-driven test (`test_table_cell_resolves_row_by_column_intersection`), fixed by skipping the header row when searching for the data row. Left in the log because it's a good illustration of why ranked, checked strategies beat a single hardcoded selector.
**v0 simplifications (documented cuts):** the `structural` strategy is a scoped CSS selector, not a true "relative path from an anchor" — true structural-path resolution was cut for time. The `visual` strategy (last-resort perceptual fallback) is unimplemented and always returns no candidates; it exists in the schema so the ranked-strategy list is complete per the brief, but nothing in v0 exercises it. Both are called out, not hidden.

## D14 — Replay engine (S6): three real bugs found by the acceptance tests, not by inspection
Building the replay engine against the real target app (not a mock) surfaced three genuine bugs, each worth keeping as evidence the design's checks actually do something:

1. **`entry.route` pointed at frame content, not the frameset shell.** The hand-written artifact's entry route was `/fr/work/inq` — correct as *content for the `work` frame*, but navigated to directly it's just a bare page with no `work` frame at all, so the entry condition's `scope: [frame: work]` could never resolve. Fixed to `/main` (the frameset page). A reminder that `entry.route` must be where a fresh session actually starts, not where a sub-frame happens to point.
2. **`Frame.child_frames` can return a stale, detached frame after a reload.** `frame_for_scope()` picked a `work` frame object from a *previous* navigation that had since been torn down, and every action on it failed with "Frame was detached". Fixed by filtering `f.is_detached()` out of the candidate list in `frame_for_scope()` — a defensive fix at the resolver level, not a one-off workaround, since any reload (not just this specific double-navigation case) could trigger it.
3. **`ElementExpectation.kind` was declared in the schema but never enforced.** The entry condition's target used `expect: {kind: "link"}` expecting that to exclude the hostile markup's deliberately hidden duplicate `<input type="submit" value="Search" style="display:none">` — but `_passes_expect()` only checked `editable` and `forbidden_text_pattern`, never `kind`. Playwright's `get_by_text()` matches an `<input>`'s `value` attribute as text, so the `text` strategy correctly reported the two controls as ambiguous (exactly what the hostile markup is designed to produce) — but with `kind` unenforced, there was no way to disambiguate. Fixed by adding a `kind`→CSS-selector check to `_passes_expect()`, reusing the same selector map the `anchor`/`table_cell` strategies already use for their `control` hint.
4. **Detectors must race the post-condition, not just explain a timeout.** The `submit_search` step's post-condition was `Any[savings_row present, "NO RECORD FOUND" present]` — satisfied by either the happy path or the not-found path. On the not-found case this "succeeded" on its own terms, so the loop moved straight to output extraction without ever checking the `member_not_found` business-outcome detector, which was only being checked *before* a step acted, or *after* a timeout — never during an outwardly-successful wait. Fixed by `_race_post_and_detectors()`: every poll tick checks armed detectors *before* the post-condition, so a business outcome always wins over a coincidentally-satisfied generic post-condition.

None of these were visible from reading the schema or the engine code in isolation — all four only showed up once real markup and a real multi-branch flow were exercised end to end, which is the argument for building the hostile target app first rather than a toy fixture.

## D15 — A fifth bug, found only by running the CLI repeatedly, not by pytest
After S6 landed, a `cua replay` CLI command was added (thin wrapper over `replay()`: scripted login, call the engine, print the typed result as JSON, exit nonzero on anything but `succeeded`/`business_outcome`). Replaying `member_no=100007` then `member_no=999999` in two separate `cua replay` processes against the same running server intermittently returned `failed(target_unresolved)` for the not-found case instead of `business_outcome` — even though `pytest` passed reliably for the identical scenario.

**Root cause:** `_race_post_and_detectors()` (D14 item 4) checks the armed detector and the post-condition as two *separate* DOM reads per poll tick (`evaluate()` calls `frame.locator("body").inner_text()` independently for each). If the "work" frame's navigation was still landing between those two reads, it was possible for the detector's read to catch the page mid-transition (not yet showing "NO RECORD FOUND") while the post-condition's read, a few milliseconds later, caught the now-settled page — letting the post-condition's own `Any[...]` fallback branch "win" the race it shouldn't have. `pytest`'s module-scoped server happened not to trigger this reliably; separate CLI processes against a freshly-started server did, consistently, once isolated.

**Decision:** after acting on a step, wait for the acted-on frame's `domcontentloaded` before starting the poll loop at all (`frame.wait_for_load_state("domcontentloaded")`, on the specific frame `step.target.scope` resolves to — not the top-level page, since the app's navigations happen inside the `work` frame, not the main frame). For a server-rendered, non-SPA app, `domcontentloaded` means the *entire* new page's content is already in the DOM, so every subsequent poll tick reads a settled state — the race window closes rather than just getting narrower.

**Verification:** 10 consecutive sequential `cua replay` runs (100007 then 999999, alternating) against one long-lived server, all correct. Not just re-run until green — the fix removes the actual mechanism (reading an in-flux DOM twice), not just the timing that happened to expose it.

**Lesson for the compiler/evidence stories:** a bug that passes `pytest` reliably but fails under a slightly different process/timing shape is exactly the kind of thing that would have made it into a demo recording undetected. Exercising the system the way a real caller would (separate process, repeated invocation) — not just through the test suite — is why this was caught before S9's proving-milestone replay runs, not during them.

## D16 — Discovery loop (S7): no translation layer between the real client and the test fixture
**Context:** S7's acceptance criteria require the loop to be fully testable offline (fixture replay, append-only history, the prose-only-end-turn → nudge → dead_end behavior) with zero LLM calls, while the *real* path has to speak the Anthropic SDK's actual computer-toolset wire format.
**Decision:** `ModelClient` is a `Protocol` with one method, `next_turn(messages) -> <something with .content and .stop_reason>`. `AnthropicModelClient` wraps the real SDK; `ScriptedModelClient` replays a fixed list of `FakeMessage`/`FakeTextBlock`/`FakeToolUseBlock` dataclasses that duck-type the exact attributes the loop reads (`.type`, `.name`, `.input`, `.id`, `.toolset_name`, `.text`). The loop never imports or type-checks against the real SDK's response classes — it only ever does `getattr(block, "type", None)` style attribute access. No translation step between "what the API returned" and "what the loop processes": the same code path runs either way, which is the point — a passing fixture test is evidence about the loop's actual logic, not about a mock that diverges from production behavior.
**Consequence:** `mypy` can't fully type-check `AnthropicModelClient.next_turn()`'s call into the SDK (it wants exact `TypedDict` params, not dict literals) — scoped `# type: ignore[call-overload]` with a comment, since that's the one code path the test suite genuinely never exercises. Every other line in `discovery/` is typed and tested.

**Action dispatch is NOT the replay engine's**, even though both now go through `resolve()` (see D17 — this paragraph originally said discovery hit-tests *after* acting; that changed). Discovery builds a `TargetDescriptor` from the hit-test facts and resolves it *before* acting (`discovery/actions.py`) — replay acts on a `TargetDescriptor` that was already reviewed and saved into the artifact (`replay/engine.py`'s `_act`). The dispatchers stay separate because their failure handling differs: discovery can fall back to a raw-coordinate click and flag the step for review when no target resolves; replay must never do that — an unresolved target is `target_unresolved`, full stop.

**Batch-action staleness (buildout plan item 13).** When one assistant turn contains several member-action `tool_use` blocks computed from a single screenshot, a page-changing action partway through the batch (e.g. a click that navigates) makes every *later* coordinate in that same batch stale — it was computed against a screen that no longer exists. Each action is followed by a cheap state-signature check (page + every live frame's URL and node count); once it changes, every remaining action in the batch gets `is_error: true, content: "screen changed; re-observe"` instead of being executed blind. Every `tool_use` still gets a paired `tool_result` (the API requires it), just not a real one. Tested directly (`test_batch_staleness_skips_remaining_actions_after_navigation`).

**What's deliberately not built yet:** the compiler that turns a discovery run into a reviewable `Capability` (S9), and `type_secret` (no current capability needs a mid-flow secret — login is fully scripted per D3; added only when a capability actually needs it, not speculatively).

## D17 — Discovery clicks resolve-then-act too (S8), and two more real bugs
**Context:** D2 already said "discovery acts through the resolved element, never the raw coordinate" — S7's first version of `discovery/actions.py` didn't actually do that (it hit-tested for *logging* only, then clicked the raw coordinate). Building S8 (the recorder) on top of that gap would have meant re-verifying equivalence after the fact, exactly the fragile pattern D1–D2 exist to avoid.
**Decision:** fixed at the source instead of papering over it in the recorder. `discovery/targeting.py` (new, shared by the dispatcher and reused by any future recorder code) builds a `TargetDescriptor` from hit-test facts — including inferring `expect.kind` from the hit element's tag (`A`→`link`, `INPUT[type=submit]`→`button`, etc.), which is what lets it disambiguate the same Search-link-vs-hidden-duplicate-button ambiguity from D14 using information already in hand. `discovery/actions.py` now resolves that descriptor and clicks the *resolved handle* — falling back to the raw coordinate, with `target=None`, only when no strategy resolves uniquely, so an unresolved step is visible in the action log rather than silently indistinguishable from a resolved one.
**Consequence:** the equivalence invariant ("what was recorded is what was acted on") is now structural, not a comparison run after the fact — there is no code path where discovery's artifact-facing target and its actual click can diverge, because they're the same resolve-then-act call.

**Two real bugs found getting here, both by stress-testing, not by a single green run:**
1. **`wait_for_load_state()` called *after* a click can race the navigation it just triggered.** The extra `resolve()` round-trip before acting shifted timing enough that the existing staleness check (D16) started flaking — 1 failure in 5 runs, reproduced and fixed, not shrugged off. `wait_for_load_state` only tells you about a navigation Playwright has already started tracking; called microseconds too early, it sees the pre-click state and returns instantly. Fixed with the correct idiom: `frame.expect_navigation()` as a context manager *wrapping* the click, so the listener attaches before the click can possibly trigger it, with a bounded timeout since most clicks don't navigate at all (a timeout here is the expected outcome, not an error). Verified with 25 consecutive clean runs (5×5), not just a second green run.
2. **Checking a claimed output against "every frame's body text" hung for ~30 seconds per run.** A `<frameset>` document has no `<body>` element at all (the frameset replaces it per the HTML spec), so `frame.locator("body").inner_text()` on the top-level frame waited out Playwright's full default actionability timeout before the broad `except` caught it — once per verification call. Fixed with an explicit short `timeout=500` on that one call. A 37-second test run was the tell; a silent 10x-slower-than-it-should-be discovery loop is exactly the kind of thing that looks "fine" until someone's waiting on a live run.

**S8's actual remaining scope**, once equivalence is structural: verify a `record_output` claim against the live page before trusting it (`discovery/recorder.py`'s `verify_output_on_page`, checking every frame's visible text for the claimed value). A mismatch escalates the run immediately (`status="escalated"`, not silently recorded) — a model claiming a value that isn't on screen is a real signal, not noise to average away.

## D18 — Locating an output's extraction target, and a navigation-timeout tuning bug
**Context:** the compiler (S9) needs every `OutputField` to carry a `target: TargetDescriptor` to re-extract on replay — but `record_output(name, value, rationale)` carries no location, only a claimed value. Without a location, the compiler would have nothing to build `extract.target` from.
**Decision:** `discovery/targeting.py`'s `locate_output_target()` searches every live frame's tables for a cell whose text contains the claimed value, and builds a `TableCellStrategy` from that cell's row-anchor and the matching column header — the same shape `resolve()` already knows how to re-find. Called inline, right after `verify_output_on_page()` succeeds, while the page is still in the state that produced the claim (same temporal-locality reasoning as D2/D17: a target built after the page has moved on is a target built from nothing). A value that isn't in a table (plain text, a list) isn't located — the output is left without a target and the compiler (S9) must flag it for manual review rather than guess one. Verified end to end: `locate_output_target` independently rediscovers the exact `row_anchor`/`column_header` pair the hand-written `member_inquiry` artifact already uses.

**A third real bug, this one a cost regression, not a correctness bug.** Wrapping *every* click in `frame.expect_navigation(timeout=1500)` (D17) is correct but expensive for the common case: a click that was never going to navigate (e.g. focusing a text field) now always pays the full timeout before `expect_navigation` gives up. Measured directly (not estimated): 1.57s for a single non-navigating click. Tuned down to `timeout=400` — on localhost, a real navigation registers within tens of milliseconds, so 400ms is generous for the true-positive case while cutting the false-wait cost roughly 4x; reverified the staleness-detection path still catches a real navigation reliably (15 consecutive clean runs) before and after the change, isolating the measurement from subprocess/browser cold-start noise (an in-process 10-repetition loop, reusing one browser, measured a steady 0.41s per non-navigating click both before and after — confirming the regression was the timeout value, not a logic bug, and that the fix addressed it directly).

## D19 — The compiler (S9): discover -> compile -> replay works end to end, offline
**Context:** this is the proving milestone's core thesis — a discovery run compiles into an artifact, and that artifact replays correctly on an input discovery never saw, with no model in the loop. `src/cua/compile/compiler.py`'s `compile_capability()` takes a completed `DiscoveryResult` and produces a `draft` `Capability`: inputs from `declare_input`, outputs from `record_output` (using the target `locate_output_target` already found, D18), outcomes from `report_outcome`, steps from every click/type `member_action`, `side_effects` from the highest step risk, provenance including the discovery run's id and a hash of the action log.
**Verified, not just asserted:** `test_compiled_capability_self_replays_on_a_different_input` discovers on member 100007 (via `ScriptedModelClient`, zero model calls), compiles, then replays the result on member **100012** — a member the discovery run never touched — through the real `replay()` engine, and checks the output against that member's real seeded balance. This is the actual end-to-end proof the brief asks for, rehearsed fully offline before spending anything on a live run.

**Three more real bugs, every one found by actually running the compiled artifact through replay — none visible from reading the compiler in isolation:**
1. **`type` actions have no target of their own, and the compiler initially required one.** Discovery's `type` action types into whatever the *preceding click* focused — it never resolves its own coordinate (there's nothing to click). The first version of the compiler required every step to carry a captured target and failed on every `type` step. Fixed by tracking the most recent click's target while walking the action log and having `type`/`type_secret` steps inherit it — which is exactly what happened in the browser, not a guess.
2. **The last step's post-condition used `OutputsPresent`, which can never become true there.** The replay engine only extracts declared outputs *after every step's post-condition has already passed* (S6's design) — so gating the last step's own post-condition on `outputs_present` is a dead end that always times out, discovered only by actually replaying a compiled artifact (`postcondition_timeout` on the final click, every single time). Fixed: the last step's post-condition checks that each output's own extraction target is resolvable (satisfiable *during* the loop); `OutputsPresent` stays correct in exactly one place — the checkpoint, which runs *after* extraction.
3. **`Capability.summary` was copied verbatim from the model's `goal_complete` text, which named the literal discovery input ("Found member 100007's balance").** A direct violation of D6's deny-by-default spirit, just on a field D6 wasn't written with in mind. Caught by the G3-style offline check (`"100007" not in yaml_text`) actually grepping the compiled artifact, not by inspection. Fixed by synthesizing the summary from the capability's structure (id, input names, output names, outcome names) instead of trusting any model-authored text to be literal-free.

**Also fixed while here:** a claimed output value shaped like money (`"1200.00"`) didn't match the DOM text it came from (`"$ 1200.00"`) because the compiler's default `transforms: [strip]` doesn't strip a currency symbol. The compiler now recognizes a money-shaped claimed value and emits `[strip, remove_dollar_sign, remove_commas, to_decimal]` with `type: decimal` — the same transform chain the hand-written artifact already used, now derived rather than hand-authored.

**What S9 does not do, by design:** synthesize detectors from `report_outcome` calls (that's a probe-run exercise — discovering what a *different*, divergent input looks like — which is S11's job, not this compiler's); infer output types beyond the money-shaped heuristic (everything else stays `type: string`); merge or dedupe near-identical steps. All documented cuts, not oversights.

## D20 — Recovery handlers (S10): detectors actually DO something now, and four more real bugs
**Context:** through S9, a `recoverable` detector firing always surfaced as a hard failure — detection existed, recovery didn't. S10 closes that: `src/cua/artifact/detector_library.py` ships four reusable detectors for this vendor app (`interstitial_notice` → dismiss + resume_step, `session_expired` → relogin + restart_entry, `app_error_500` / `permission_denied` → hard failures), and the replay engine actually *runs* a recoverable detector's handler — dismiss (click a target), relogin (call a caller-supplied `login_fn`, never a dynamic lookup of `script_ref`, keeping D3 intact), backoff (wait) — then resumes, retries, or restarts per the handler's `then`, bounded by both a per-detector `max_attempts` and a whole-run `MAX_RUN_RECOVERIES` (5) budget. `commit_irreversible` steps refuse `retry_step` outright, and `restart_entry` is refused on any capability containing one, since a restart always replays every step from the beginning.

**Four more real bugs, every one found by actually running a recovery, not by reading the handler code:**
1. **The same "no `<body>`" hang as D18, found a *second* time** — this time in `replay/checks.py`'s shared `evaluate()`, not `recorder.py`. A library detector's `TextPresent` has no `scope` (it should match in whichever frame shows it), and an empty scope fell back to `page.main_frame` — the frameset's bodyless top document — so every unscoped detector check waited out Playwright's ~30s default timeout. Fixed the same way as D18 (`timeout=500`), but this time generalized: an empty scope now searches *every live frame* and concatenates their text, which is what "unscoped" should mean for a condition in the first place, not an accident of which frame happens to be `main_frame`.
2. **`LocationMatches` only checked `page.url`, which never changes for a frame-level redirect.** The `session_expired` fault redirects whichever *frame* made the request (e.g. the `work` frame's own form POST) to `/login` — the top-level page's URL never moves, since the frameset itself never navigates. The detector's `route_pattern=r"/login$"` against `page.url` alone could never match. Fixed by checking every live frame's URL, matching if any does.
3. **The interstitial's "Continue" link 405'd on a POST-triggered fault.** `target_app`'s own bug, not the engine's: `<a href="{{ continue_url }}">Continue</a>` does a GET, but the route that triggered the interstitial (`POST /fr/work/inq/result`) only has a POST handler — clicking Continue landed on `{"detail":"Method Not Allowed"}`, not the real result. Fixed by capturing the original request's form data when the trigger was a POST and rendering Continue as a self-submitting form with hidden inputs reconstructing it, instead of a plain link. The detector library's dismiss target was loosened from `expect.kind="link"` to unconstrained, since the control's tag now depends on how it was triggered (`<a>` for a GET, `<input type=submit>` for a POST) — safe here because only one such control exists on this page at a time either way, so there's nothing to disambiguate.
4. **`engine.py` crossed the 400-line guideline once handler execution was added for real** (482 lines). Split along existing seams rather than trimmed: `replay/recovery.py` owns detector matching and handler execution (`RecoveryState`, `run_handler`, `armed_detector`, `race_post_and_detectors`), `replay/steps.py` owns the per-step primitives (`run_action`, `wait_for`, the output transform chain), and `engine.py` is left as just the act → wait → recover → advance/restart loop. All 49 tests re-verified passing after the split — a refactor is only as good as its test suite proves it didn't change behavior.

**Verified against the real fault-injection app**, not a synthetic stand-in, for the cases that matter: interstitial dismissal and session-expiry relogin+restart both end in `succeeded` with the correct balance and `result.recoveries` naming exactly which detector fired; `http500`/`permission_denied` are hard failures; a synthetic `commit_irreversible` step refuses `retry_step` with `recovery_exhausted`; an always-matching detector trips the 5-recovery run budget exactly at the 6th attempt.

## D22 — The act() choke point (S12): a network-level guard, not a per-action classifier
**Context:** S12 needed one place where "can this agent's traffic go here" and "can this agent commit a side effect" are enforced — not scattered through step dispatch, where it's easy to add a new action type later and forget the check. `src/cua/safety/policy.py` installs a single `page.route("**/*", ...)` handler before any step runs. Because it sees every *network request* regardless of what triggered it — an explicit `page.goto`, a clicked link, or a plain form submit fired by pressing Return in a field — there's no separate "was this an Enter-key submit vs a button click" classification to get wrong: both produce the identical POST, and the guard only ever looks at the request. Off-origin requests and any POST to a configured `commit_routes` prefix on a `read_only` capability are aborted outright; a commit-route POST on a write-capable capability is gated on `safety/approval.py`'s single-use `ApprovalStore` (D23).
**Alternative considered:** classify risk from the `Step.risk` field the compiler already assigns, and gate *there* instead of at the network layer. Rejected: `Step.risk` is a static, per-step label assigned once at compile time from what discovery happened to click — it can't see what a step's action actually *does* on the wire (e.g. a `press` of Return triggering an implicit submit that no `Step.risk` was ever assigned to, since discovery only logged it as a keypress). The network layer sees the real HTTP method and path every time, independent of how replay got there.

## D23 — Approval records, keyed to exact inputs, not just capability identity
**Context:** `ApprovalStore.decide()` (`src/cua/safety/approval.py`) keys a grant on `capability_id:version:effective_sha256:sha256(canonical_inputs_json)` — not just the capability's identity. An approval granted for "transfer $50 to checking" must never silently cover a replay with a different amount, and an approval for one artifact version must never apply after the artifact is edited (the content hash changes). `decide()` checks and consumes in the same call, so there's no window between "is this approved" and "mark it used" for a second concurrent replay attempt to also observe "approved" before either one consumes it.

**Two real bugs found replaying the hand-written `transfer_funds` capability against the actual app (not a synthetic one — S12 wires real `/fr/work/xfer/*` routes into `target_app`, reusing the templates S2 had left unrouted):**
1. **`page.goto("javascript:...")` never produces a network request at all** — confirmed directly by installing the guard and watching `page.route` simply never fire for it. A network-level choke point structurally cannot see a `javascript:` URI, so "block javascript:" can't live in `policy.py`. It has to be refused earlier, and *narrowly*: the real app's own "Search" link uses `href="javascript:document.forms['srch'].submit()"` — a classic link-triggered-submit pattern — and a blanket block on every `javascript:` href broke that legitimate, already-passing step. The actual side effect of that pattern is the resulting form POST, which the network guard *does* see. So the block is scoped to the one place a literal, directly-controlled URL is handed to `page.goto` — the `navigate` action in `replay/steps.py` — not to every incidentally-encountered `javascript:` href while clicking through real app UI.
2. **The route handler recording a violation runs asynchronously, and checking `policy_state.latest()` immediately after `click()` returns raced it** — confirmed by observing a policy-denied commit fall through to a slow `postcondition_timeout` instead of an immediate `policy_denied`. `click()` resolving, and even the settle frame's `wait_for_load_state("domcontentloaded")` (which doesn't block on an aborted request — nothing new loads), doesn't guarantee Playwright's route callback has actually run yet. Fixed with the same shape as every other Playwright race in this codebase (D8's `expect_navigation`/400ms tuning): a short bounded `page.wait_for_timeout(200)` after acting, only when a policy guard is installed, before checking for a violation.

**Verified against the real app**: a read-only capability's commit attempt is denied outright (`policy_denied`, `commit_blocked_read_only`); a write-capable capability with no approval record blocks (`blocked_pending_approval`); with a matching record it succeeds, returns a real `confirmation_no` extracted from the receipt page, and consumes the record; replaying again with the same (now-consumed) record is a hard `policy_denied` (`commit_reused_approval`), not a second pending-approval state. The off-origin and plain-POST-is-unaffected cases are also exercised directly against the live app.

## D24 — Detector synthesis is a probe-run exercise, verified at runtime, not by string comparison (S11)
**Context:** the happy-path discovery run `compile_capability` works from never sees a business-outcome page, so it emits no detectors (D19). `src/cua/discovery/outcome_probe.py` is the deliberately separate exercise: run discovery again against an input expected to diverge (e.g. `999999`, a member that doesn't exist), let it call `report_outcome`, then diff that page's *visible* text against the happy page's visible text to find what's actually unique to the outcome. "Visible" matters specifically: `inquiry_result.html` hides `NO RECORD FOUND - RC=04` in a `display:none` div on the happy page as a trap for an implementation that reads `textContent` — the diff and the resulting detector both go through `replay.checks.visible_page_text()`, the same `innerText`-based reading `TextPresent` itself uses, so a correct implementation can't help but pass this negative control, and an incorrect one (reading `textContent`) would see the hidden trap text as "shared with the happy page" and silently build a weaker or wrong detector. The negative control (`passes_negative_control`) re-*evaluates* the synthesized condition against a live happy page through the real `Condition` evaluator — never a string-equality check against saved text — because the thing that must not fire in production is the evaluator, not a snapshot.

**One real bug found:** the first implementation picked the *longest* unique line as the signal, which happened to be `"Member 999999 was not located."` — the probed literal itself baked into the detector. Caught by the compiler's own deny-by-default precedent (D6) applied here: `_probed_literals()` now collects every value the probe run actually typed and excludes any unique line containing one before ranking by length, so a detector built from probing one member number doesn't silently only ever match that number.

## D25 — Relabel drift (S11): fallbacks have to be added at every label-dependent site, not just the one that was asked about
**Context:** a tenant that relabels this app's UI text (`target_app/data.py`'s `LABELS_RELABELED`) swaps *displayed* strings only — `member_inquiry`'s `$labels.search_btn` reference is substituted against the **capability's own** `labels` dict (the base set), never the server's active one, so a relabeled server breaks every strategy and condition that names a label, regardless of which step it's attached to. Demonstrating "replay survives a relabel" for real (not just the one step the AC names) meant finding and fixing *three* separate label-dependent sites in the hand-written `capabilities/member_inquiry/0.0.1.yaml`, each discovered by actually replaying against a relabeled server and watching it fail in a new place each time a prior one was fixed:
1. `submit_search`'s own click target — fixed with a `structural` fallback strategy, `path: "a"` (the work frame has exactly one `<a>` tag either way, so this resolves uniquely regardless of label text). This is the one `StepTrace.drifted` actually flags: resolution fell through to a strategy other than the first-ranked one.
2. `enter_member_no`'s *post-condition* — a separate, independently-authored `TargetDescriptor` literal for the same Search control, which needed the identical fallback added by hand; it is not automatically kept in sync with the step's own target.
3. The `savings_balance` output's extraction target (`table_cell`, keyed on `$labels.savings_row`/`$labels.balance_col`) and `submit_search`'s own post-condition text check — neither has a meaningful non-label fallback *strategy*, since they're plain text/cell lookups, not element targets with a strategy list. Fixed by switching to label-independent signals instead: the extraction target gained a `structural` fallback (`table[border='1'] tr:nth-child(2) td:nth-child(2)` — the balance table is the only bordered one on this page, with exactly one data row, regardless of its header text), and the post-condition / checkpoint text checks were changed to key off `{{ inputs.member_no }}` (echoed back verbatim on both outcome pages) instead of a label.

**Takeaway recorded here rather than left implicit:** a target's ranked strategies give drift-resistance for free; a condition that only has `text`/`pattern` to work with does not, and has to be redesigned around something structurally stable (an echoed input, a unique table shape) instead. `StepTrace.drifted` only ever reports on case 1 — it has no way to see 2 or 3, since those aren't `TargetDescriptor` resolutions at all. Verified end-to-end against the real relabeled app: `enter_member_no` resolves via `attr` (`drifted=False`, untouched by relabeling at all), `submit_search` resolves via `structural` (`drifted=True`), and the whole run still reaches `succeeded` with the correct extracted balance.

## D26 — Redaction has to run at two different chokepoints, not one (S13)
**Context:** text and pixels leak PII through different paths, so one redaction function can't cover both. `src/cua/safety/redaction.py` handles text — SSN/DOB fixed-shape patterns, Luhn-validated digit runs (a checksum, not just "N digits", so an ordinary 12-digit reference number that fails the checksum isn't false-flagged), and a caller-supplied list of exact literals for anything that doesn't shape-match a pattern (e.g. a plain 6-digit member number, which is only "sensitive" because the capability declared it `sensitivity="pii"`, not because it looks like anything). `src/cua/evidence/writer.py`'s `write_run_transcript` is the actual chokepoint for text: the one place a run's `action_log`/summary leaves memory and touches disk, so it's the one place that calls `redact_text` before writing. `src/cua/safety/visual_redaction.py` handles the other path — a screenshot shows PII as pixels, which no text function can touch — by blacking out a known region before the screenshot is taken, not after (there's no "redact a PNG after the fact" step to forget to call).

**The realistic leak this was built against:** not `record_output` (already gated — D6/D9's deny-by-default literal handling only lets a *declared* value into a compiled artifact) but a real LLM's own narration. A model doing discovery routinely describes what it sees in its reasoning — "I can see member 100007's record, born 1978-04-17" — and nothing in `discovery/tools.py`'s schema ever asks it to declare that as sensitive; it's just ordinary `thinking` content, logged verbatim into `action_log`. The canary test (`tests/integration/test_canary.py`) seeds exactly this via a `FakeThinkingBlock`, runs a real discovery session, writes the transcript, and asserts zero hits for the seeded DOB (pattern-caught) and member number (declared-literal-caught) anywhere under the output root — verified as non-vacuous by checking the *unredacted* transcript actually contains both first.

**One real bug found building the pixel-masking half, not by inspection:** the first version injected the mask `<div>` into the top-level `page`'s DOM using page-absolute coordinates. It silently did nothing — no exception, but nothing painted. Cause: this app's frameset top document has no real `<body>` (D18/D20's recurring fact, biting a third subsystem); per the HTML5 body-element algorithm, `document.body` on a frameset document resolves to the `<frameset>` element itself, which doesn't composite arbitrary block children the way a real body does. Fixed by injecting into the *target frame's own* document instead (`frame.evaluate`, not `page.evaluate`) — which in turn meant converting the box to that frame's local coordinates (`element_handle.bounding_box()` always returns page-absolute coordinates, confirmed directly, even for an element nested inside an iframe), by subtracting the frame's own absolute offset. Verified against actual decoded pixels (Pillow, test-only dependency — never imported by `src/`): the masked region's center is pure black, a point outside it is not.

# REPORT

A computer-use automation system for a legacy, API-less banking UI: an LLM discovers how to operate it once; that run compiles into a typed, reviewable **capability** artifact; the artifact replays deterministically forever after with zero model calls; a human can take over mid-run when the system gets stuck; and a set of guardrails stand between the agent and anything irreversible or sensitive.

Everything named below is real, built, and tested against a real browser and a real (mock) target app — see `docs/DECISIONS.md` for the full decision log (D0–D29) and every bug found building it, and the root `README.md` for how to run any of it yourself.

## Architecture

The system is three pipelines that share one artifact format, plus two cross-cutting layers.

**Discover** (`src/cua/discovery/`) — a loop (`loop.py`) that hands a live `Page` and a goal to a `claude-opus-5-5` model equipped with the `computer_toolset_20260801` tool type plus six custom strict tools (`tools.py`): `declare_input`, `record_output`, `assert_checkpoint`, `report_outcome`, `request_human`, `goal_complete`. The model never acts on a raw coordinate — every click/type is **resolved then acted on** (`discovery/targeting.py` builds a checked `TargetDescriptor` from hit-test facts before `discovery/actions.py` ever touches the DOM), so what gets logged is a target discovery actually verified, not a coordinate that happened to work once. The `ModelClient` boundary (`discovery/model_client.py`) is a `Protocol` with two implementations — the real Anthropic client, and a `ScriptedModelClient` that replays a fixed sequence of turns — and the loop code is identical either way, because the fixture duck-types the exact same attributes the real SDK response carries. This is what makes ~95% of this system's testing possible with zero API cost (D16).

**Compile** (`src/cua/compile/compiler.py`) — turns a completed `DiscoveryResult` into a draft `Capability`. Deny-by-default on literals: every typed value must trace back to a `declare_input` call, or compilation fails outright rather than silently baking a raw discovery literal into a reusable artifact (D6). The compiler also builds each step's post-condition from the *next* step's target (the last step's from its outputs' own extraction targets — never `OutputsPresent`, which can't be true until after extraction runs, a bug found by actually replaying a compiled artifact, D19), and classifies risk from member-action text against a commit-word vocabulary.

**Replay** (`src/cua/replay/`) — the deterministic engine. `engine.py` is the per-step act → wait → recover → advance/restart loop; `steps.py` is the act/resolve/wait-for-condition primitives; `recovery.py` is detector matching and handler execution; `checks.py` evaluates the condition language. `replay/` never imports `anthropic` — enforced by a dedicated test that greps the package for the string — because discovery and replay are architecturally separate code paths: one costs tokens and is non-deterministic, the other is free and must never be (D9).

**Cross-cutting:** `src/cua/safety/` (policy guard, approval store, text + pixel redaction) sits between replay and the live page; `src/cua/control/` (the control lease, CDP operator attach) sits between discovery and a human; `src/cua/evidence/` writes a redacted, reviewable record of any run to disk. `src/cua/surface/` (frame-aware hit-testing, the ranked-strategy resolver) is shared by both discovery and replay — the same `resolve()` function that locates a target during a live discovery click also locates it during a compiled replay, so there's exactly one place "find this element" can go wrong, not two.

`target_app/` is a deliberately hostile mock legacy banking app (FastAPI + Jinja2): a frameset shell whose top-level document has no `<body>` at all (a fact that has caused real bugs in three separate subsystems — D18, D20, D26), nested tables, no test IDs, duplicate/hidden submit controls, POST-based forms, and an injectable fault controller (`target_app/faults.py`) for interstitials, slow responses, HTTP 500s, permission errors, session expiry, and tenant relabeling.

## Artifact schema

`Capability` (`src/cua/artifact/schema.py`) is the typed, versioned contract an agent invokes and replay runs without a model: `status` (draft/approved), `side_effects` (read_only/reversible_write/irreversible_write), `labels`, `inputs`/`outputs`/`outcomes`, `entry`, `steps`, `detectors`, `checkpoint`, `provenance`, an optional `review`. Every model in the schema sets `extra="forbid"` — a structural anti-coordinate guarantee: nothing can smuggle an undeclared field through the artifact, since that's exactly the kind of silent drift a reviewable artifact exists to prevent.

A `Step`'s `target` is a `TargetDescriptor` (`artifact/targets.py`): a `scope` (frame-nesting path), an `ElementExpectation` guard (kind/editable/forbidden-text-pattern — catches resolving onto the wrong element after drift), and a **ranked list of independently-checkable strategies** — `attr`, `role`, `anchor`, `table_cell`, `text`, `structural`, `visual` — tried in order. The resolver (`surface/resolve.py`) never falls back to a first match on ambiguity: a strategy that matches more than one element is rejected outright and resolution falls through to the *next* strategy; if nothing resolves uniquely, the target is `target_unresolved`. This ranked-strategy design is also what makes drift-resistance possible at all (see Heterogeneity, below).

The condition language (`artifact/conditions.py`) — `TextPresent`, `ElementResolvable`, `LocationMatches`, `OutputsPresent`, `AllOf`/`AnyOf`/`NotCondition` — is what a step waits on, a detector matches against, and a checkpoint asserts. It's deliberately small and composable rather than growing a new primitive per use case.

The replay result contract (`replay/result.py`) is a Pydantic discriminated union: `Succeeded | BusinessOutcomeResult | Failed{code, step_id, expected, observed, retryable} | Escalated | BlockedPendingApproval`. A caller can `match` on `status` and know exactly what happened — "the member doesn't exist" (`business_outcome`) is structurally distinct from "the UI broke" (`failed`), which is distinct from "a human needs to look at this" (`escalated`), which is distinct from "this needs explicit sign-off before it can proceed" (`blocked_pending_approval`).

## Determinism & error handling

Replay is a pure function of `(capability, inputs, a live page)` — no model call anywhere in `replay/`. Every step follows the same discipline as discovery: **resolve, then act**, never act on a stored coordinate. `StepTrace` records which strategy actually resolved each step and whether it was the target's first-ranked one (`drifted: bool`) or a fallback — a signal, not a failure, that the surface has moved since discovery saw it.

Errors are typed, not stringly: `FailureCode` is a closed `Literal` (`target_unresolved`, `postcondition_timeout`, `checkpoint_mismatch`, `app_error`, `recovery_exhausted`, `policy_denied`, `outcome_unknown`, `input_invalid`). Recoverable faults are handled by detectors (`artifact/detector_library.py` ships four reusable ones for this vendor app: an interstitial notice, session expiry, HTTP 500, permission denied) whose `recoverable` kind runs a `Handler` — `dismiss` (click a target), `relogin` (call a caller-supplied `login_fn`, never a dynamic lookup of a script-ref string), `backoff` (wait) — then resumes, retries, or restarts per the handler's `then`, bounded by both a per-detector `max_attempts` and a whole-run recovery budget (`MAX_RUN_RECOVERIES = 5`). `commit_irreversible` steps refuse `retry_step` outright, and `restart_entry` is refused on any capability containing one, since a restart always replays every step from the beginning — a half-committed irreversible action must never be retried blind.

A recurring lesson, documented because it actually cost debugging time more than once: this app's frameset has no real `<body>`, so an unscoped/unguarded Playwright locator action against the top document waits out the ~30s default actionability timeout before failing. Found and fixed in `discovery/recorder.py`, then independently in `replay/checks.py`'s text-matching, then a third time in `safety/visual_redaction.py`'s screenshot masking — three different subsystems hitting the identical root cause, each found by actually running the thing and watching it hang, not by code review.

## Heterogeneity & multi-tenant

The design stance: a capability is bound to one vendor/product/version-range (`AppBinding`) and carries its own `labels` dict. A different tenant of the *same* underlying app that relabels its UI text (`target_app/data.py`'s `LABELS_RELABELED` — e.g. "Member No." → "Acct Holder ID", "Search" → "Find") is handled by substituting `$labels.x` references against the capability's own labels, not by the resolver adapting automatically — multi-tenancy here is a human-reviewable **overlay** (a different `labels` dict, possibly a different capability version), not implicit runtime magic.

What *is* automatic is drift-resistance within that model: a target's ranked strategies let replay survive a relabeled tenant without any label overlay at all, as long as at least one strategy doesn't depend on the relabeled text. `member_inquiry`'s search-button step carries both a `text` strategy (fast, fails under relabeling) and a `structural` fallback (`path: "a"` — the one anchor tag in that frame, regardless of its label) — proven in `tests/integration/test_outcome_probe.py` against the real relabeled app: the step falls through to the `structural` strategy, `StepTrace.drifted` records that it did, and the run still reaches `succeeded` (D25). Three separate label-dependent sites needed this treatment (the step's own target, a copy of the same target embedded in the *previous* step's post-condition, and the output-extraction target) — a target's strategy list gives drift-resistance for free, but a bare text/pattern condition doesn't, and has to be redesigned around something structurally stable (an echoed input value, a table shape that's unique regardless of its header text) instead.

Probe discovery (`discovery/outcome_probe.py`, S11) is the other heterogeneity-facing piece: a capability compiled from one happy-path discovery run never sees a business-outcome page, so a *second*, probe-input discovery run is what synthesizes a `business_outcome` detector — by diffing the probe page's visible text against the happy page's, excluding any line containing a literal the probe run itself typed (so a detector built from probing member `999999` doesn't silently only ever match `999999`). The negative control that gates acceptance re-evaluates the synthesized condition against a live happy page through the real `Condition` evaluator, not a string comparison — which matters concretely here, since the happy page hides the exact outcome text in a `display:none` trap div specifically to catch an implementation that reads `textContent` instead of visible text.

## Escalation & handoff

Three distinct "something's not straightforwardly fine" states, each structurally different: `BusinessOutcomeResult` (a legitimate, declared outcome — "this member doesn't exist" — not a failure), `Escalated` (discovery/replay can't proceed and needs a human), `BlockedPendingApproval` (the *system* can proceed but policy requires explicit sign-off first — see Safety).

For `Escalated`, S14 adds a real live handoff, not just a terminal state. `discovery/loop.py`'s `request_human` call, when a `ControlLease` (`control/lease.py`) is supplied, hands the lease to a human and waits (bounded, `handoff_timeout_s`) instead of returning immediately. The human side (`control/operator.py`, and `cua control status`/`cua control release`) attaches over CDP to the **same already-running browser** the agent was driving — `playwright.chromium.connect_over_cdp`, a second client to one browser, not a fresh one — so whatever the human sees and fixes is the actual live DOM state the agent was stuck on. On release, discovery doesn't restart: it folds "a human took over, made changes, and handed control back" into the same tool-result turn (not a second back-to-back user message, which would violate the API's role-alternation requirement) and resumes from wherever the screen now is. A human who never shows up still degrades to the old `escalated` result rather than hanging forever. Every handoff — resumed or not — is recorded in the action log (`human_handoff`, with `resumed: bool`), the same audit discipline recovery and policy decisions already follow.

## Safety

Three independent guardrails, each covering a different failure mode, verified against the real app rather than mocked:

**Deny-by-default literals** (compiler, D6): a typed value only ever enters a compiled artifact if it traces back to a `declare_input` call. This is what stops a raw discovery-session literal (a specific member number, say) from silently baking into a capability meant to be reused with different inputs — caught in practice by the compiler's own summary field once, which had leaked a literal through the model's own `goal_complete` text (fixed by synthesizing summaries structurally instead of trusting model prose, D19).

**The act() choke point** (`safety/policy.py`, S12): a single `page.route("**/*", ...)` network guard installed before any step runs — not a per-action classifier, because a step's declared `risk` can't see what actually happens on the wire (a Return-key submit and a button click produce the identical POST; the network layer sees both the same way, with no separate "was this Enter" classification to get wrong). It blocks off-origin requests outright and gates any POST to a configured commit route behind `safety/approval.py`'s single-use `ApprovalStore`, keyed to `capability_id:version:effective_content_hash:sha256(canonical_inputs)` — so an approval for "transfer $50 to checking" can never cover a different amount, and check-and-consume happen atomically so a second concurrent replay can't also observe "approved" before either consumes it. `javascript:` navigation is blocked separately, in `replay/steps.py`'s `navigate` action, narrowly: a `javascript:` URI never produces a network request at all (confirmed directly — the route guard simply never fires for one), and a blanket block on every `javascript:` href would have broken the mock app's own legitimate `href="javascript:document.forms[...].submit()"` link-triggered-submit pattern, which is exactly the kind of thing a real legacy app does. Verified end to end against a real hand-written `transfer_funds` capability and real `/fr/work/xfer/*` routes: no approval → `blocked_pending_approval`; with one → succeeds, returns a real confirmation number, consumes the record; reusing it → a hard `policy_denied`, not a second approval.

**Redaction** (`safety/redaction.py`, `safety/visual_redaction.py`, S13): text redaction (SSN/DOB patterns, Luhn-validated digit runs — a checksum, not just "N digits", so an ordinary non-card-shaped number isn't false-flagged — and a caller-supplied declared-literal list) runs at the one chokepoint a run's text actually touches disk (`evidence/writer.py`). Pixel redaction blacks out a known PII-bearing screen region before a screenshot is taken, since text redaction can't touch an image. The canary test (`tests/integration/test_canary.py`) seeds a leak through the realistic path — a model's own `thinking` narration of what it sees, which nothing in the tool schema gates — and asserts zero hits anywhere under the evidence output root, verified as non-vacuous by confirming the *unredacted* transcript really does contain the seed first.

## Cuts

Scoped down deliberately, and recorded here rather than left implicit:

- **`structural` strategy is a scoped CSS selector, not a true anchor-relative path.** Good enough to demonstrate drift-resistance on this app's actual markup; a production version would want relative-to-anchor traversal, not a flat selector that happens to be unique today.
- **`visual` strategy is unimplemented.** It always returns no candidates — an honest "this last-resort fallback doesn't exist yet" rather than a stub that pretends to work.
- **Multi-tenant relabeling needs a hand-added fallback strategy per label-dependent site**, found by actually replaying against a relabeled tenant and watching each one fail in turn (D25). A production compiler would want to infer these automatically from a single discovery run, or require two (base + relabeled) before accepting a capability as tenant-portable.
- **The approval store is in-memory**, not persisted — fine for demonstrating the mechanism, not for a real multi-process deployment where the thing granting approval and the thing consuming it aren't the same Python process.
- **`cua replay`'s CLI doesn't wire up the policy/approval gate** — it's exercised directly through `replay()`'s `policy`/`approval_store` parameters in tests, not end-to-end through the CLI, since there's no commit route configured for the demo `member_inquiry` capability to protect.
- **No production `cua discover` CLI command.** Discovery is invoked through the Python API (tests, `scripts/collect_evidence.py`) and one capped dev spike (`scripts/spike_g0.py`); a real CLI entry point for live discovery runs was out of scope for this pass.
- **The required real, live `claude-opus-5-5`-driven discovery run (with its own `/evidence/` output) hasn't been run yet.** `evidence/demo_member_inquiry/` is a real, working demo of the full pipeline, built and run for real — but with a `ScriptedModelClient` standing in for the API, by design (zero incidental API spend while iterating). The real run is a deliberate, one-time, capped step, gated behind sign-off to spend API credit, same as the G0 spike.
- **Recovery/backoff timings are fixed constants**, not adaptively tuned (`MAX_RUN_RECOVERIES = 5`, a 200ms policy-settle wait, etc.) — each one was derived from observing a specific real race condition, not from a general tuning pass.
